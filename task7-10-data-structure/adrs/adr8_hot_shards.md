### Название задачи: выявление и устранение «горячих» шардов.
### Автор: Михейчев И.С.
### Дата: 4.02.2026
### Функциональные требования

|**№** |**Инициатор**|**Use Case**|**Описание**|
|---|---|---|---|
| F1.1 | pymongo_api | Выявление перегруженных шардов | Система принимает решение о том, что шард перегружен и необходимо перераспределить нагрузку |
| F1.1 | pymongo_api | Перераспределение нагрузки | Система осуществляет перераспределение нагрузки |

### Нефункциональные требования

|**№**|**Требование**|**Комментарий**|
|---|---|---|
|       | **Надёжность (Reliability)** |
| R1.1  | Шарды расходуют память равномерно | Неравномерный расход уменьшает надежность, например из-за OOM |
| R2.1  | Запросы распределяются между шардами равномерно | Перегрузка некоторых шардов увеличивает риск DoS |
| R3.1  | Операции с шардами равномерно загружают CPU | Перегрузка некоторых шардов увеличивает риск DoS |
|       | **+ Ограничения (Restrictions)**       |
| R+1.1 | Ни один шард не занимает памяти сверх лимита | Выход за лимиты ведет к OOM |
| R+2.1 | Ни один шард не использует процессор сверх лимита | Перегрузка шарда увеличивает риск DoS |

### Решение

Метрики шарда:
- Количество занимаемой шардом памяти (shard_volume);
- Количество запросов к шарду (shard_reqs);
- Время работы СУБД при обработке запроса к шарду (shard_cpu);

Обоснование метрик:
- shard_volume необходима для контроля общих лимитов и равномерности распределения в памяти.
- shard_reqs помогает оперативно реагировать на перегруз так как для сбора shard_cpu нужно время, за которое система может упасть.
- shard_cpu позволяет защититься от ложных срабатываний, вызванных большим количеством быстро обрабатываемых запросов. Формат метрики (время за период или % от всего объёма) может быть выбран исходя из удобства реализации.
  
Способы получения метрик описаны в [документе](../docs/metrics.md).  

Критерии перегруженности шарда:
1. По памяти:
    1. shard_volume превосходит порог Th<sub>1</sub> (~90% от доступной);
    2. shard_volume расходится для разных шардов более чем на X<sub>1</sub> (~30%).
2. По вводу/выводу:
    1. shard_reqs расходится для разных шардов более чем на X<sub>2</sub> (~50% с учетом burst).
3. По вычислительной мощности:
    1. shard_cpu превосходит порог Th<sub>2</sub> (~80%);
    2. shard_cpu расходится для разных шардов более чем на X<sub>3</sub> (~30%).

Обоснование критериев:
1. Критерии по памяти направлены на контроль общего потребления памяти и равномерности распределения данных.
2. Критерий ввода-вывода. Направлен на оперативное выявление потенциальной перегрузки, должен использоваться в связке с критериями по вычислительной мощности.
3. Критерии по вычислительной мощности направлены на контроль общего потребления и равномерности использования вычислительных ресурсов. Данные критерии должен быть использован в связке с критерием ввода-вывода, что позволяют избежать ложных срабатываний при большом количестве "лёгких" запросов.

Способы перераспределения данных описаны в [документе](../docs/shards_redistribution.md).

Выбор механизма перераспределения данных:
- Если нарушен критерий 1.1, то необходимо увеличить количество шардов или общие лимиты на кластер.
- Если нарушен критерий 1.2, стоит применить автоматическую балансировку так как присутствует неравномерность, с которой Mongo должен справиться.
- Если нарушены критерии 2.1, 3.1 или 3.2, а также в случае непродуктивности автобалансировки, необходимо: произвести анализ, выявить наиболее горячие данные и произвести перераспределение вручную. При нарушении этих критериев данные могут быть распределены равномерно, но некоторые из них более популярны (много запросов), либо участвовать в более "тяжелых" операциях (потребление cpu), потому Mongo не сможет эффективно распределить их в автоматическом режиме.
